# Production RAG Optimization Playbook

每个生产优化点：为什么这么设计、怎么验证、踩过什么坑。

## 1. 检索优化（Retrieval）

### Hybrid Search（向量 + BM25）
- **为什么**：纯向量检索对专有名词（订单号、人名、型号）不敏感，BM25对精确匹配好。两者互补。
- **怎么验证**：建50题eval集，分别跑纯向量/Hybrid，看Recall@5。
- **坑**：BM25权重别超过0.4，否则长文档被稀疏匹配污染，语义就丢了。

### Chunk Size
- **为什么**：太大（>1500）会把不相关内容混进一个chunk，检索命中率低；太小（<300）会切碎上下文，LLM答不出完整答案。
- **怎么验证**：同一eval集，跑chunk 300/600/800/1200，对比。
- **坑**：条款类文档按句切分（`\n`），别按字符硬切，否则条款被切断。

### Reranking（重排）
- **为什么**：检索返回Top20，但LLM上下文有限。Cross-Encoder重排把最相关的5条排前面。
- **怎么验证**：对比rerank前后Eval的Answer Relevancy。
- **坑**：Reranker要选和业务同域的（法律用法律rerank，代码用代码rerank），通用模型效果差。

## 2. 生成优化（Generation）

### Guardrail（防幻觉）
- **pre-check**：检索到的上下文和问题相关吗？不相关直接拒答，别硬编。
- **post-check**：答案里每个事实都能在上下文找到吗？找不到就删掉/标[不确定]。
- **怎么验证**：Faithfulness指标，>0.85才算合格。

### 温度（Temperature）
- **为什么**：知识问答要温度0.2以下，答案要稳定；创意写作才用0.7+。
- **坑**：温度太高，同样的问法每次答案都不一样，客户投诉。

## 3. 性能优化（Performance）

### 缓存（Redis）
- **为什么**：重复问题不重复调LLM，省成本、降延迟。
- **怎么验证**：同一问题连问10次，命中缓存后延迟<100ms。
- **坑**：缓存要有TTL，知识库更新后要失效旧缓存，否则答旧内容。

### 流式输出（Streaming）
- **为什么**：用户看到第一个字延迟<1秒，体验好。等全答完要5秒，用户跑了。
- **坑**：流式+检索+多轮，要处理好中间状态，别把检索日志也流给用户。

### 异步任务（Celery）
- **为什么**：文档上传/切分/embedding是重任务，同步做会阻塞API。用Celery后台跑，前端显示"处理中"。
- **坑**：要支持重试，embedding超时自动重试3次。

## 4. 评估优化（Evaluation）

### Eval集
- **怎么建**：从真实用户日志里抽50-100个问题，人工写标准答案。分领域（客服/HR/产品）。
- **指标**：
  - Context Precision：检索到的上下文相关吗？
  - Faithfulness：答案有没有幻觉？
  - Answer Relevancy：答案答对题了吗？
- **怎么用**：每次改参数跑一遍eval，对比涨跌。分数涨了才保留。

### 迭代节奏
1. 建eval集（半天）
2. 跑基线（10分钟）
3. 改一个参数（如chunk 600→800）
4. 跑eval对比
5. 涨了保留，降了回退
6. 一次只改一个变量

## 5. 部署优化（Deployment）

### 数据库
- Dev用SQLite，Prod换PostgreSQL（并发，事务）。
- **坑**：SQLite不支持并发写，多租户上传文档会崩。

### 向量库
- Dev用Chroma，Prod换Pinecone（托管，不用运维）。
- **坑**：Chroma是本地嵌入式，百万级向量撑不住。

### 缓存
- Dev用内存，Prod换Redis（多实例一致）。

### 监控
- LangSmith追踪每次检索/生成的trace。
- 告警：Faithfulness < 0.8 或 延迟 > 2s 触发告警。

## 6. 多租户优化（Multi-tenant）

### 数据隔离
- **为什么**：A公司的知识库不能让B公司看到。
- **方案**：每个租户一个向量库namespace + 数据库行级隔离。
- **坑**：检索时忘了加tenant过滤，串数据——这是最严重的生产事故。

> "我做了一个企业级RAG平台，4个场景。核心是：Hybrid检索+重排保证召回，Guardrail防幻觉，Redis缓存省成本，Celery异步处理重任务，eval集驱动参数调优。生产部署用PostgreSQL+Pinecone+Redis，多租户数据隔离。骨架两天能写，但调优花了我三周——检索不准、幻觉、延迟，每个都是踩坑踩出来的。"
